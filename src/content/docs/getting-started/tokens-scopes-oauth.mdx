## Token Taxonomy

| Token | Prefix | Represents | Typical use |
|---|---|---|---|
| Bot token | `xoxb-` | The app's own bot user | Almost everything -- a stable identity independent of any individual member |
| User token | `xoxp-` | A specific workspace member | Actions that must appear as performed by that person |
| App-level token | `xapp-` | The app itself, across every workspace it's installed in | Socket Mode (`connections:write`) and other app-wide operations |
| Workflow token | `xwfp-` | A single Workflow Builder step, briefly | Reading data inside that step only -- expires 15 minutes after issuance or when the step finishes, whichever comes first |

Taxonomy per [Tokens](https://docs.slack.dev/authentication/tokens/). This site's patterns default to the bot token -- it's the only one of the four that isn't tied to a person, a workflow run, or Socket Mode.

:::warning[Workflow tokens and the Lists API]
`xwfp` tokens carry "borrowed visibility" into channels the workflow's initiator can see but the bot user isn't a member of -- useful inside Workflow Builder, but at least one community report shows a workflow-token call against `slackLists.access.set` returning `list_not_found` where the same call on a bot token would work ([slackapi/deno-slack-sdk#472](https://github.com/slackapi/deno-slack-sdk/issues/472)). That's not documented Slack behavior, just a field report -- treat it as a reason to keep list writes on the bot token rather than a workflow token. See [Lists: Access & Scopes](../lists/access-and-scopes.mdx) for the list-specific access model.
:::

## Minimal Scope

Request only the bot scopes a feature actually uses, and add more later rather than everything up front -- scopes are additive on reinstall (below), so there's no cost to growing the list over time, and every unused scope is a permission you'd have to justify if the workspace admin ever audits installed apps ([Installing with OAuth](https://docs.slack.dev/authentication/installing-with-oauth/)).

## Installing Without An OAuth Redirect

Slack's OAuth v2 flow exists to let *any* workspace install *your* app: the user is redirected to Slack, approves the requested scopes, and Slack redirects back to a URL your server hosts with a temporary code your server exchanges for a token. None of that applies to an app that only ever runs in the one workspace you built it for. Clicking **Install to Workspace** on the app's own **OAuth & Permissions** page *is* the installation -- Slack issues the token immediately and shows it on that same page, with no redirect URL, no code exchange, and no server-side callback to write ([App distribution](https://docs.slack.dev/distribution)).

## When OAuth Is Needed

The full redirect flow matters once the app leaves your workspace: **public distribution** (any workspace can install it via a shareable link) and **org-wide internal distribution** (installable across every workspace in an Enterprise Grid org) both require implementing the redirect endpoint, because Slack has no other way to hand your server a token for a workspace it doesn't run in. Multi-workspace distribution is out of scope for this release -- everything here assumes a single, known workspace.

## Reinstalling After A Scope Change

Scopes are additive: requesting a new scope and sending the workspace through install again adds it to the existing grant rather than replacing it, and there's no way to downgrade a token's scopes short of reinstalling with a smaller manifest ([Installing with OAuth](https://docs.slack.dev/authentication/installing-with-oauth/)). Editing the manifest or the scope list alone changes nothing live -- Slack's manifest guidance notes that updating a manifest doesn't modify tokens already issued to a workspace ([App distribution](https://docs.slack.dev/distribution)) -- so a newly added scope has no effect until the workspace goes through **Reinstall to Workspace** again, and the token issued before that reinstall never gains it.

The full sequence, in order:

1. Add the scope to the manifest or the **OAuth & Permissions** scope list.
2. Click **Reinstall to Workspace**.
3. Compare the token now shown on **OAuth & Permissions** against the stored secret. Reinstalling *may* issue a new bot token, but that isn't guaranteed by Slack's docs -- observed across repeated reinstalls of a production reference integration, rotation has gone both ways: sometimes a new token, sometimes the same one back.
4. If the token changed, set the new value as the Worker secret and verify it works ([Worker Backend: Secrets & Config](../worker-backend/secrets-and-config.mdx)) *before* treating the old token as invalid -- Slack doesn't revoke the previous token as part of reinstalling, so there's no rush. If it's unchanged, there's nothing to rotate.
5. Deploy -- this pushes the rotated secret if step 4 applied, and ships any code that depends on the new scope.
6. Enable the event subscriptions the new scope unlocks. A scope grant doesn't retroactively subscribe the app to the event types it makes available.
